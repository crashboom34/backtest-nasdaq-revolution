# E3-E — K1 Étape 2, B3 v5-A : tables fermées des artefacts K1 et sorties Walk-Forward hachées — note technique LOCALE, NON NORMATIVE

**Statut (2026-10-25).** Implémenté et testé **en local, sans commit ni push**, sur le checkpoint `5cb911a` (D8/B2 et B5 format 2 publiés). L'utilisateur a autorisé cette première tranche de B3 v5 (reconnaissance structurelle des artefacts K1, tables fermées, lecture contrôlée, règles `HASHED_FILE`) **sans** accepter R9, D1-D9 ni E3-E dans leur ensemble. **Hors périmètre, non commencé :** nouveau `SourceKind` d'E3-A, verdict d'absence d'exposition, nouveau FRESH fondé sur K1, écrivain RESERVATION/ADMISSION, vérificateur L3 (chaîne couverture-sessions-sceau), couverture `DERIVED`, `evidence_hash`, E3-J, accès FINAL_HOLDOUT, moteurs et stratégies. `REAL` = DISABLED / NOT QUALIFIED · `GATE V` = NON PASSÉE · `FINAL_HOLDOUT` = NON ACCÉDÉ.

**Ce que B3 v5-A est.** Une **table de sources** plus large, qui TYPE des fichiers que v4 traitait comme entrées inconnues, et les lit sans les interpréter. **Ce que B3 v5-A n'est pas :** une preuve. Un fichier reconnu reste une source **non résolue** : `UNRESOLVED` (jamais `RESOLVED`, jamais `NO_OVERLAP`) et une raison d'incomplétude. Ni une couverture syntaxiquement valide (preuve de lecture réelle), ni un sceau valide (preuve de chronologie), ni une liste de sorties hachées (preuve d'exhaustivité) ne lèvent quoi que ce soit : cela relève du futur vérificateur L3.

## 3. Comportement scientifique (garde centrale)
| Situation | v4 | v5-A |
|---|---|---|
| sortie `walk_forward/**` hachée sans anomalie | dossier inconnu : raison `UNKNOWN_ENTRY` + finding `UNKNOWN_SOURCE`/`UNRESOLVED` | raison **`RUN_OUTPUT_UNVERIFIED`** + finding `UNKNOWN_SOURCE`/`UNRESOLVED`/cause `WINDOW_UNKNOWN`, `content_hash` = SHA-256 des octets bruts (lie la sortie à `inventory_id`) |
| preuve de run (couverture/session/sceau) conforme | fichier inconnu bloquant | raison **`RUN_EVIDENCE_UNVERIFIED`** + finding non résolu avec le hash des octets |
| preuve non conforme (L2, identifiant ≠ dossier, numéro ≠ fichier, DERIVED, octets non normatifs, version) | fichier inconnu bloquant | raison `INFORMATIVE_UNRESOLVED` + finding `INVALID_SCHEMA` |
| illisible / JSON invalide / trop gros / nature fausse | anomalie | inchangé (chemin de B3 : raison `SOURCE_ANOMALY` ou `UNKNOWN_ENTRY` + finding) |
| orphelin d'une cible connue | `UNKNOWN_TEMP_FILE` bloquant | raison **`RUN_ORPHAN`** + finding `UNKNOWN_SOURCE_TYPE` : reconnu, **jamais lu, jamais la sortie attendue, jamais supprimé, toujours bloquant** |
| **répertoire** de sorties reconnu (`walk_forward`, `folds`, `fold_NNN`, `.gate_v_checkpoints_v1`, `…/folds`), **même vide** | dossier inconnu bloquant | raison `RUN_OUTPUT_UNVERIFIED` + finding non résolu sans hash (un dossier de fold n'est créé qu'**après** le calcul du fold : un squelette vidé est la trace d'un calcul). *Défaut démontré par la revue indépendante (squelette vide → `complete=True`, FRESH en v5, bloqué en v4) ; corrigé par TDD.* |
| fichier attendu absent | rien | rien (une absence n'est jamais une preuve ; `MISSING_REQUIRED` pour l'ancre `validation_run.json`) |
| `.tmp` forgé, mauvais dossier, mauvaise casse de hex, double suffixe | inconnu bloquant | inconnu bloquant (identique) |

## 5. B5 / A0
- `HASHED_RULES_DIGESTS` = **exactement** `{(v5, CAMPAIGN_DIR, aa389aca…10af)}` ; le littéral y est répété indépendamment du module v5 (double clé) et un test vérifie qu'il égale la table publiée ; **aucun triplet historique** (v2, v3, v4) n'est inscrit (test explicite).
- Concordance exécutable (`unregistered_hashed_tables`) : toute table réellement utilisée comportant une règle `HASHED_FILE` est inscrite avec son digest recalculé, et toute table inscrite en comporte une. Table hachée non inscrite : le producteur **refuse** (aucun inventaire ne peut s'appuyer dessus). Table inscrite sans `hash_limits` : refus. `hash_limits` sur une table non hachée : refus.
- Un inventaire v5 avec une racine de campagne s'écrit en **format 2** (25 clés, `hash_limits` = les plafonds RÉELLEMENT appliqués) ; un inventaire v5 sans table hachée s'écrit en **format 1** historique (24 clés) avec la version v5 enregistrée ; un inventaire v4 s'écrit et se relit comme avant (A0 doré inchangé).
- Version et digest doivent concorder : digest v4 sous la version v5, ou digest v5 sous la version v4 → `RULES_DIGEST_MISMATCH` ; version inconnue → `UNKNOWN_VERSION`. Une modification d'un octet d'un budget change le hash de contenu et le nom.
- Le registre est une **DÉCLARATION**, pas une preuve d'exécution : un `ExposureScan` forgé reste la limite documentée (E3-J recalcule).
