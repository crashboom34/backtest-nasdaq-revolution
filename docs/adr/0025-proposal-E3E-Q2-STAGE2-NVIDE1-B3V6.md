## 2. Contrat implémenté (règles A-J de la décision)
**Architecture.** `gate_v_exposure_interpreters_v6.py`, module frère : `interpret_audit_roots_v6(roots, limits, *, hash_limits, holdout_window_*, hooks=None)` appelle l'interprétation v5 **puis** ajoute des raisons dérivées des observations du scan de **cette** invocation (jamais un objet d'appelant). Conséquences par construction : raisons de v6 ⊇ raisons de v5, findings / scans / plans / évidences **identiques** (aucun finding ni hash fabriqué, aucun `SourceKind`), `hooks_used` conservé, erreurs de structure et d'instabilité de B2 propagées. La table de reconnaissance est celle de v5 (mêmes objets) : `rules_digest` **égal** à celui de v5, constaté par recalcul indépendant (algorithme de B2 et oracle écrit à part) et non imposé ; la version sémantique est distincte (`gate_v_exposure_interpreters_v6`).
**Preuve positive exigée** pour toute raison : manifeste lu strictement sans anomalie, conforme au schéma de B3 (`_manifest_v2_conforms`), propre au dossier de campagne ; puis un état d'activité / d'échec / d'incomplétude, une référence explicite, ou une contradiction. Un dossier vide seul n'est pas converti ; un manifeste absent ne crée aucune attente (I) ; `exposure/` vide : aucun comportement ajouté (J).
**Raisons (typées, déterministes, `CODE:<racine>/manifest.json#<référence>`)** : `MANIFEST_RUN_IN_PROGRESS` (C), `MANIFEST_TECHNICAL_FAILURE` (D, **sans** convertir l'échec en exposition), `MANIFEST_EVIDENCE_INCOMPLETE`, `MANIFEST_RUN_ABSENT` (B, G), `MANIFEST_RUN_EVIDENCE_MISSING` (F : pièces `run_data_coverage.json`, ≥ 1 `run_session_NNNN.json`, `run_seal.json` du run référencé), `MANIFEST_RUN_FOREIGN`, `MANIFEST_RUN_ID_INVALID`, `MANIFEST_STATE_CONTRADICTION` (`running_vs_status`, `failure_reason_vs_status`, `ready_vs_activity`, `ready_vs_revision`, `complete_vs_references`), `MANIFEST_ARTEFACTS_WITHOUT_EXECUTION`. Règle E : `EVIDENCE_COMPLETE_AWAITING_FINAL_HOLDOUT` exige les références WF, MC et PS (contrat D2) ; une pièce référencée manquante est signalée. Règle H : MC/PS présents ne lèvent aucune raison non résolue de v5.
**`ready_vs_revision`** (ajout après la relecture indépendante) : le producteur réel (`gate_v_campaign_manifest_v2.py`) incrémente la révision à chaque commande et `execution_started` ne revient jamais à faux ; un manifeste READY de révision > 0 est donc une preuve POSITIVE d'activité passée portée par le manifeste lui-même (pas une inférence tirée d'un dossier vide).
**Identités.** Pour toute entrée sans raison nouvelle, `inventory_id`, classification et refus de préconditions sont **identiques** à v5 (littéraux historiques gelés dans les tests). Une entrée qui devient incomplète reçoit une **nouvelle** identité d'inventaire v6 (acceptable : nouvel inventaire) ; aucune identité historique n'est réécrite.

## 3. B5 / A0 (modifications strictement requises)
Trois ajouts dans `gate_v_exposure_store.py` : import des constantes de v6 ; triplet haché `(v6, CAMPAIGN_DIR, aa389aca…10af)` dans `HASHED_RULES_DIGESTS` (même table, même digest que v5) ; v6 ajoutée aux versions lisibles et à la table des digests connus. `RulesVersions.is_current()` reste lié à v4 (**aucune décision d'activation**) ; formats A0 1 et 2 inchangés ; `hash_limits` et leur sémantique inchangés ; un A0 v6 sans table hachée s'écrit en format 1, avec table hachée en format 2 strict. Un digest v4 sous la version v6, ou le digest v6 sous la version v4, est refusé (`RULES_DIGEST_MISMATCH`) ; v7 est `UNKNOWN_VERSION`. **Limite documentée** : v5 et v6 ayant le même digest, un A0 « relabellisé » v5↔v6 n'est pas détecté par le digest (B5 n'authentifie pas cryptographiquement un A0 ; E3-J recalcule).
**Relabelling v5 ↔ v6 (audit final, 2026-11-02 ; deux tests de caractérisation, `test_gate_v_exposure_store_v6.py`).** (a) *Altération détectable* : changer `rules_versions.b3_interpreters` d'un A0 (v5→v6 ou v6→v5) SANS recalculer `inventory_content_hash` est refusé (`HASH_MISMATCH`). (b) *Falsification avec recalcul d'authenticité* : si l'auteur recalcule le hash de contenu et le nom de fichier, l'A0 est relu sous l'autre version (le `rules_digest` est identique car la table est identique) ; aucune formule d'identité ne dépend de la version de B3, donc `inventory_id` est inchangé, et la version relue n'est jamais « courante ». Un `rules_digest` identique n'est PAS une équivalence sémantique (v6 ajoute des raisons que le digest ne couvre pas) : la garantie « cet inventaire a été produit par v6 » n'est portée par aucun digest. Limite documentée, non corrigée ; la requalification relève d'E3-J (recalcul).
**Tests historiques actualisés (4 assertions, intention conservée)** : `test_gate_v_exposure_store_v5.py` ×3 (registre = triplets v5 ET v6 ; boucle limitée aux triplets v5 ; première version inconnue = v7) et `test_gate_v_exposure_v4_v5_differential.py` ×1 (garde « seul B5 référence v5 » : v6 est désormais le seul autre consommateur, il appelle l'interpréteur v5 par construction ; v6 n'est lui-même importé que par B5, vérifié par un test).

## 6. Risques résiduels
(1) v6 est un module **non activé** : tant qu'aucun appelant d'audit n'utilise `interpret_audit_roots_v6`, v4 reste la version courante et le défaut subsiste pour tout consommateur de v4/v5 — l'activation est une décision distincte. (2) EVIDENCE_INCOMPLETE et toute campagne « complète » restent bloquées (aucun producteur n'écrit encore la chaîne couverture/session/sceau) : c'est le comportement voulu, pas un défaut. (3) Les identifiants de fold ≥ 1000 donneraient `MANIFEST_RUN_ID_INVALID` (v4 les traite déjà comme dossiers inconnus). (4) Un manifeste restauré à l'identique d'un manifeste initial (révision 0) est indiscernable de l'original : relève de N-VIDE-2 / E3-J (chronologie). (5) Une clé PS dont le suffixe ne correspond pas à l'identifiant n'est pas signalée (le run est alors absent, donc signalé, ou présent et non résolu).
